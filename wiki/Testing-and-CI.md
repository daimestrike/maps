# Тесты и CI

## Проверки локально

```sh
npm run check              # tsc --noEmit, без сборки
npm run build              # prisma generate + next build
npm run test:integration   # сквозной тест по живому HTTP
```

## Интеграционный тест

`tests/integration.mjs` — один сценарий на `node:assert`, работает через реальные HTTP-запросы к запущенному приложению и заодно заглядывает в базу через Prisma. Запускается с `--env-file=.env`, адрес берёт из `APP_URL`.

```sh
npm start &                 # или npm run dev
npm run test:integration
```

Успех — строка `PASS: …` в выводе. Ненулевой код возврата означает провал.

Что проверяется:

- анонимный `GET /api/stores` получает 401;
- регистрация с чужим `Origin` получает 403;
- регистрация двух пользователей проходит, cookie выдаётся;
- в базе лежит bcrypt-хеш (начинается с `$2`), а не сам пароль;
- повторная регистрация того же email — 409;
- вход с неверным паролем — 401, с верным — 200;
- поиск по `?search=` находит созданный магазин;
- карточка возвращает правильный регион;
- `PATCH` сохраняет изменения и сбрасывает `coordinatesApproximate` в `false`;
- `POST /api/geocode` отвечает с `approximate: true`;
- магазин, созданный без координат, получает `coordinatesApproximate: true`;
- комментарий без сессии — 401; пустой и длиннее 2000 символов — 400;
- автор комментария берётся из сессии, `passwordHash` в ответе отсутствует;
- текст комментария реально сохранён в PostgreSQL;
- второй пользователь видит комментарий первого с его именем и временем;
- постранично: 50 записей на первой странице, 2 на второй, все 52 разные;
- выход отзывает сессию — `GET /api/auth/me` после него даёт 401;
- сессия второго пользователя тоже отзывается.

После себя тест удаляет созданные записи: временных пользователей с уникальным суффиксом в email, тестовый магазин и комментарии. Запускайте на локальной или тестовой базе с открытой регистрацией — на рабочую базу не направляйте.

## GitLab CI

`.gitlab-ci.yml`, одна стадия `test`, образ `node:22-bookworm-slim`, рядом сервис `postgres:17-alpine`. Последовательность: `npm ci` → `db:migrate` → `db:seed` → `build` → `check` → `npm start` в фоне → `test:integration`. Логи сервера печатаются в `after_script` в любом случае, включая падение. Учётные данные в переменных пайплайна одноразовые, для временной базы.

## GitHub Actions

`.github/workflows/offline-bundle.yml` — «Build offline server bundle», запускается вручную (`workflow_dispatch`). Собирает образ под `linux/amd64` с кешем в GitHub Actions cache, затем проверяет развёртывание по-настоящему:

1. поднимает `compose.prod.yaml` целиком;
2. ждёт `healthy` до 10 минут;
3. сверяет, что в таблице `Store` ровно 25 680 записей;
4. выполняет вход под `admin@x5.local` через `/api/auth/login`.

Только после этого пакует `images.tar.gz` вместе с `compose.prod.yaml`, `deploy.sh`, `.env.production.example` и `OFFLINE-README.md` в архив и выкладывает артефактом на 30 дней. Логи стека печатаются и стек сносится в `trap` при любом исходе.

Проверка «ровно 25 680» — это защита от тихой потери каталога: если миграция или импорт сломаются, сборка упадёт, а не выпустит пустой архив. При замене каталога своими данными это число в workflow нужно обновить.

## Ручная проверка

Стоит прогонять после изменений в интерфейсе — автотестов на UI нет:

1. Войти под `ivan@example.com`, найти магазин по коду, открыть карточку.
2. Отправить комментарий, обновить страницу, снова выбрать магазин — комментарий на месте.
3. В другом браузере войти под `anna@example.com` — комментарий виден с автором «Иван (демо)».
4. Клик по маркеру открывает карточку, при уменьшении масштаба маркеры собираются в кластеры.
5. Отредактировать карточку: значения сохранились, надпись о приблизительных координатах исчезла, маркер переехал.
6. Добавить магазин без координат — координаты определились, в карточке отмечены как приблизительные.
7. Проверить на узком экране (около 400 px): панели не ломают вёрстку.
