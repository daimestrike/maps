# Каталог магазинов

## Что лежит в репозитории

| Файл | Размер | Назначение |
|---|---|---|
| `prisma/data/stores.csv` | 13,5 МБ | 25 680 магазинов с уже посчитанными координатами. Разделитель `;`, кодировка UTF-8 с BOM |
| `prisma/migrations/202609210001_store_catalog/migration.sql` | 16 МБ | Тот же каталог в виде `INSERT` — чтобы свежая база была работоспособна сразу после миграций |
| `public/russia-regions.geojson` | 907 КБ | Контуры регионов, рисуются под маркерами и работают без интернета |

Колонки CSV: `ID`, `Территория`, `Макрорегион`, `Дивизион`, `Кластер`, `ЦФО`, `МВЗ`, `№ завода SAP`, `Наименование магазина`, `Код формата магазина`, `Наименование формата магазина`, `Юридическое лицо`, `Регион`, `Город`, `Метро`, `Адрес`, `Время работы`, `Широта`, `Долгота`, `Источник координат`.

`№ завода SAP` служит и кодом магазина (`code`), и значением `sapPlant`. Оба поля уникальны в базе.

## Откуда координаты

**В исходной выгрузке координат нет — только адреса.** Их добавляет `scripts/prepare-stores-data.mjs` из открытой базы GeoNames по географии России, без обращения к онлайн-сервисам геокодирования.

```sh
npm run data:prepare -- <исходный.csv> <RU.txt> [prisma/data/stores.csv]
```

`RU.txt` — файл почтовых кодов GeoNames (`postalCodes/RU.zip` с https://download.geonames.org/export/zip/): табулированный, где важны колонки индекс, населённый пункт, регион, широта, долгота.

Алгоритм для каждой строки, по убыванию точности:

1. **Почтовый индекс** — шесть цифр в начале адреса, точное совпадение с индексом GeoNames. Разброс ±0,004°, это сотни метров.
2. **Населённый пункт** — поле «Город», затем части адреса через запятую. Названия нормализуются: нижний регистр, `ё` → `е`, отбрасываются суффиксы `г.`, `город`, `пгт.`, `рп.`, `с.`, `д.`. Разброс ±0,012°.
3. **Регион** — по названию региона. Разброс ±0,08°, это десятки километров.
4. **Территория** — центр одной из пяти территорий (Центр, Северо-Запад, Юг, Волга, Восток), иначе центр Москвы. Тот же разброс ±0,08°.

Колонка `Источник координат` в CSV хранит, какой шаг сработал: `postcode`, `locality`, `region` или `fallback`.

**Зачем разброс.** Все магазины с одним индексом получили бы одну и ту же точку и слились в один маркер. Поэтому к координате добавляется детерминированный сдвиг, посчитанный хешем FNV-1a от кода магазина: у каждого магазина своя точка, и при повторной подготовке данных она не меняется.

**Следствие: все координаты из каталога приблизительные.** В базе у них `coordinatesApproximate: true`, в карточке это видно по надписи «Координаты рассчитаны приблизительно по адресу». Точность от сотен метров до десятков километров — зависит от того, какой шаг сработал. Для точных координат их нужно подтвердить: отредактировать карточку (это сбрасывает флаг) или заменить каталог выгрузкой, где координаты уже есть.

## Как заменить каталог своими данными

Если в вашей выгрузке координат нет:

1. Приведите файл к тем же колонкам (обязательны `№ завода SAP`, `Наименование магазина`, `Регион`, `Город`, `Адрес`; скрипт падает, если какой-то из них нет).
2. Скачайте и распакуйте `RU.zip` с GeoNames.
3. `npm run data:prepare -- ваш.csv RU.txt` — перезапишет `prisma/data/stores.csv`. Скрипт напечатает, сколько записей получили координаты на каждом шаге.
4. `FORCE_STORE_IMPORT=true npm run db:seed`.

Если координаты у вас уже есть — добавьте колонки `Широта` и `Долгота` в CSV самостоятельно, шаг подготовки не нужен, только seed. Проверьте диапазоны: широта −90…90, долгота −180…180, иначе вставку отклонит CHECK-ограничение базы.

Импорт идёт через `upsert` по коду: комментарии и магазины, добавленные вручную, сохраняются, но **ручные правки полей у магазинов из каталога перезаписываются**.

Встроенная миграция `202609210001_store_catalog` содержит исходный каталог и на уже применённой базе повторно не выполняется, так что менять её при замене данных не нужно.

## Офлайн-геокодер

`src/lib/geocode.ts` определяет координаты по адресу, когда магазин добавляют или редактируют через интерфейс. Внешние сервисы не вызываются — точка выводится из **уже загруженного каталога**:

1. Если в адресе есть шестизначный индекс — берутся до 50 магазинов, чей адрес начинается с этого индекса.
2. Иначе — до 100 магазинов того же города (без учёта регистра).
3. Иначе — до 100 магазинов того же региона.
4. Ничего не нашлось — 422, координаты нужно ввести руками.

Из найденных считается среднее арифметическое широт и долгот — центр тяжести соседних магазинов. Поэтому точность зависит от того, насколько плотно район уже покрыт каталогом, а на пустой базе геокодер не работает вовсе.

Результат всегда помечается как приблизительный: `POST /api/geocode` возвращает `approximate: true`, а созданный без координат магазин получает `coordinatesApproximate: true`.

## Тайлы карты

По умолчанию карта берёт тайлы с публичного сервера OpenStreetMap — нужен интернет. Атрибуция сохранена, офлайн-кеша и массового скачивания нет.

`NEXT_PUBLIC_TILE_URL=off` **на этапе сборки** убирает слой тайлов совсем: остаются контуры регионов и маркеры. Именно так собирается Docker-образ — поэтому в контейнере карта работает без интернета, но без подложки с улицами. Свой сервер тайлов подключается тем же способом, с шаблоном URL вместо `off`.

Для корпоративной нагрузки выбирайте источник тайлов с учётом [политики OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/). Список магазинов и комментарии наружу не уходят, но запросы тайлов раскрывают, какую область карты смотрят.
