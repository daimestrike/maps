# Границы MVP

Что сознательно не сделано, где пределы текущих решений и какой следующий шаг в каждом случае.

## Нет ролей и разграничения доступа

Любой авторизованный пользователь видит всю сеть и все комментарии, может отредактировать любую карточку и добавить магазин. Ролей, прав и ограничений по территории нет.

*Дальше:* поле роли у пользователя и проверка в эндпоинтах; при появлении SSO — маппинг групп на роли.

## Аутентификация только по email и паролю

SSO, LDAP, двухфакторной аутентификации, восстановления пароля и подтверждения email нет. Открытая регистрация не проверяет, что адрес корпоративный — поэтому после создания нужных аккаунтов ставьте `ALLOW_REGISTRATION=false`.

Вся логика вынесена в `src/lib/auth.ts` именно для того, чтобы её можно было заменить, не трогая остальной код.

*Дальше:* корпоративный SSO вместо содержимого `auth.ts`.

## Комментарии нельзя изменить или удалить

Только добавление и чтение. Ни автор, ни администратор не может отредактировать или убрать комментарий через интерфейс — правки только напрямую в базе. Уведомлений, упоминаний, вложений, реакций и обновления в реальном времени тоже нет: новые комментарии появляются после нажатия «Обновить».

*Дальше:* мягкое удаление с сохранением истории, а не физическое.

## Вся карта грузится одним запросом

`GET /api/stores` отдаёт все 25 680 магазинов сразу, поиск и фильтрация идут на клиенте. Маркеры кластеризуются и добавляются порциями, список показывает первые 100 совпадений — на карте видны все.

На текущем объёме это работает. Первая загрузка — самый тяжёлый момент экрана, и он линейно растёт вместе с каталогом.

*Дальше, когда станет тесно:* отдавать магазины по границам видимой области карты и перенести поиск на сервер. Серверный поиск через `?search=` уже реализован — интерфейс его просто не использует.

## Координаты приблизительные

В исходной выгрузке координат не было, они рассчитаны по индексу, городу или региону из открытой базы GeoNames и разведены детерминированным сдвигом, чтобы маркеры не слипались. Точность — от сотен метров до десятков километров. Все такие записи помечены `coordinatesApproximate: true`, и в карточке это видно.

Офлайн-геокодер в интерфейсе усредняет координаты уже загруженных соседних магазинов, то есть на пустой базе и в непокрытых районах не работает.

*Дальше:* выгрузка с настоящими координатами либо разовое геокодирование по надёжному источнику. Подробности — [[Store Catalog|Store-Catalog]].

## Тайлы карты

По умолчанию — публичный сервер OpenStreetMap, нужен интернет. Офлайн-кеша нет, массового скачивания тайлов нет, атрибуция сохранена. В Docker-образе слой тайлов отключён на сборке, поэтому остаются только контуры регионов и маркеры.

*Дальше:* свой сервер тайлов во внутренней сети и `NEXT_PUBLIC_TILE_URL` на него при сборке. Учитывайте [политику OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/) — на корпоративную нагрузку публичные тайлы не рассчитаны.

## Нет админ-панели и импорта из интерфейса

Пользователями, каталогом и массовыми изменениями занимаются через скрипты и SQL. Загрузить CSV через браузер нельзя — только `npm run data:prepare` и `npm run db:seed`.

Помните: повторный импорт каталога перезаписывает поля магазинов, изменённые вручную (совпадение по коду). Комментарии и магазины, добавленные через интерфейс, при этом не страдают.

## Нет истории изменений

Кто и когда поправил карточку — не записывается. Есть только `updatedAt`. Аудита действий нет.

*Дальше:* таблица истории изменений, если правки станут частыми.

## Ограничение попыток входа неполное

10 попыток на email за 15 минут, общие для всех экземпляров приложения. Перебор пароля по множеству разных адресов и ограничение по IP не покрыты — это задача reverse proxy. См. [[Security]].

## Тестами покрыт только сквозной сценарий

Один интеграционный тест на API плюс проверка типов. Юнит-тестов, тестов компонентов, браузерных и нагрузочных тестов нет. Интерфейс проверяется руками по списку из [[Testing and CI|Testing-and-CI]].

## Эксплуатационная обвязка снаружи

HTTPS, ограничение по IP, CSP, автоматические бэкапы, ротация логов, алерты — всё настраивается вокруг приложения, внутри его нет. `/api/health` отвечает, пока жив процесс Next.js, и состояние базы не проверяет.

## Перед промышленным запуском стоит сделать

1. Заменить каталог выгрузкой с подтверждёнными координатами.
2. Подключить SSO и закрыть самостоятельную регистрацию.
3. Ввести роли, если править карточки должны не все.
4. Поднять свой сервер тайлов.
5. Настроить HTTPS, ограничение по IP и CSP на reverse proxy.
6. Настроить регулярные бэкапы PostgreSQL и мониторинг `/api/health` вместе с `pg_isready`.
7. Измерить время первой загрузки на реальном объёме и, если он вырос, перейти на загрузку по границам карты.
