# Безопасность

Сервис рассчитан на внутренний контур: внутренняя сеть или VPN, HTTPS через reverse proxy. Ниже — что реализовано в коде и что обязательно донастроить снаружи.

## Пароли

- bcrypt, cost 12. В базе только хеш.
- Минимум 12 символов, максимум 72 байта — верхний предел задан самим bcrypt, который молча обрезает более длинный вход. Проверка считает **байты**, а не символы: русские буквы занимают по два.
- При входе с несуществующим email пароль всё равно сравнивается — с фиктивным хешем. Время ответа одинаковое, по нему нельзя определить, есть ли такая учётная запись.
- Ответ на неверный вход один и тот же — `Неверный email или пароль`, без уточнения, что не совпало.

## Сессии

- Токен — 32 случайных байта из `crypto.randomBytes`.
- В базе хранится **только SHA-256 от токена**. Дамп базы не даёт войти ни под кем.
- Cookie `x5_session`: `HttpOnly` (JavaScript её не прочитает), `SameSite=Lax`, `path=/`, срок 7 дней. Флаг `Secure` — по `COOKIE_SECURE`.
- Вход отзывает предыдущую сессию этого же браузера и попутно удаляет все истёкшие записи.
- Выход удаляет серверную запись, а не только cookie: украденный токен после выхода бесполезен.
- Срок проверяется при каждом запросе, на стороне сервера.

## Авторизация запросов

Каждый эндпоинт вызывает `currentUser()` сам и отвечает 401 без сессии. Глобального middleware нет намеренно — так не появится маршрут, который «должен был» попасть под защиту, но не попал.

Что следует из этого:

- **Все данные доступны любому авторизованному пользователю.** Ролей нет: кто вошёл, тот видит всю сеть, все комментарии и может править любую карточку и добавлять магазины. Разграничение доступа — задача следующего этапа ([[Limitations]]).
- Автор комментария берётся исключительно из сессии. Поле `userId` во входных данных не читается — подменить авторство нельзя, это закреплено тестом.
- Наружу отдаются только `id` и `name` автора. `passwordHash` и email в ответах комментариев не появляются — тоже проверяется тестом.

## Защита от CSRF

Любой запрос, кроме GET, обязан прислать `Origin`, совпадающий с origin из `APP_URL`; иначе 403. Вместе с `SameSite=Lax` это закрывает межсайтовую подделку запросов. Токенов CSRF нет — они бы ничего не добавили при такой проверке.

Практическое следствие: `APP_URL` должен точно соответствовать адресу, по которому открывают сервис, иначе перестанут работать все изменения данных. Это самая частая ошибка развёртывания ([[Operations]]).

## Валидация входных данных

- Все схемы — Zod, в `src/lib/validation.ts`. Ручного разбора полей нет.
- Лимит тела запроса — 16 КБ, поток обрывается при превышении, ответ 413. Большой JSON не займёт память.
- Требуется `Content-Type: application/json`, иначе 415.
- Длины ограничены на обоих уровнях: комментарий 2000 символов и в Zod, и как `VARCHAR(2000)` в PostgreSQL; координаты проверяются Zod и CHECK-ограничением базы.
- Пользовательский текст выводится React как текст. HTML из комментариев не исполняется. `dangerouslySetInnerHTML` в коде нет.
- Все запросы к базе идут через Prisma с параметрами — SQL-инъекция невозможна, сырых запросов в коде нет.

## Ограничение попыток входа

10 попыток на email за 15 минут. Счётчик — в PostgreSQL (`AuthAttempt`), поэтому работает одинаково при любом числе экземпляров приложения, в отличие от счётчика в памяти процесса. В ключе — SHA-256 от адреса, сами email в таблице не лежат.

**Чего этот лимит не делает:** он не мешает перебирать пароль по множеству разных адресов и не ограничивает запросы с одного IP. Для сервиса, доступного из интернета, добавьте ограничение по IP на reverse proxy — встроенного нет.

## Заголовки ответов

`next.config.ts` ставит на все ответы:

| Заголовок | Значение |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` — встроить в iframe нельзя |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

`X-Powered-By` отключён. Ответы API идут с `Cache-Control: no-store` — ни браузер, ни промежуточный прокси их не кеширует.

CSP не настроен — стоит добавить на reverse proxy, с учётом того, что Leaflet требует `img-src` для источника тайлов.

## Обработка ошибок

Наружу уходит либо понятное сообщение (`HttpError`, ошибка валидации, конфликт уникальности), либо обобщённое `Не удалось выполнить запрос. Попробуйте позже.` — трассировка стека попадает только в лог сервера. Тексты ошибок валидации на русском и рассчитаны на показ пользователю.

## Что нужно донастроить снаружи

| Что | Почему |
|---|---|
| HTTPS через reverse proxy + `COOKIE_SECURE=true` | Next.js не терминирует TLS; без HTTPS токен сессии идёт открытым текстом |
| Ограничение доступа сетью или VPN | Аутентификация не проверяет, что email корпоративный |
| `ALLOW_REGISTRATION=false` после создания аккаунтов | Иначе зарегистрироваться может любой, кто дошёл до страницы |
| Ограничение запросов по IP на прокси | Встроенный лимит не защищает от перебора по разным адресам |
| CSP | В приложении не задан |
| Резервные копии PostgreSQL | Комментарии и правки восстановить больше негде ([[Operations]]) |
| Завершение сессий после перехода на HTTPS | Cookie, выданные по HTTP, остаются валидными до конца срока |

## Прочее

- Секретов в репозитории нет: `.env` исключён `.gitignore`, в шаблонах только заглушки. Пароли в `.gitlab-ci.yml` и в workflow GitHub — одноразовые, для временных баз CI.
- `deploy.sh` генерирует пароли из `/dev/urandom` и создаёт `.env` с `umask 077`.
- Данные магазинов и комментарии никуда не передаются. Единственный внешний запрос приложения — тайлы карты, и они раскрывают только область просмотра. В офлайн-сборке внешних запросов нет вовсе.
